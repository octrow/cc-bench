# cc-bench

Это инструмент для тестирования (бенчмаркинга) инструментов Claude Code в формате «до/после». Он позволяет взять связку
«целевой репозиторий + инструмент» (это может быть навык, CLI-утилита, MCP-сервер или артефакты вроде OpenSpec) и
получить объективную, воспроизводимую оценку того, **действительно ли этот инструмент помогает**. Полученные данные
достаточно надежны для принятия архитектурных решений (ADR).

## Две категории инструментов

- **Категория P (probes / проверки).** Это инструменты, которые меняют то, *как* ИИ-агент собирает контекст (например:
  rtk, graphify, gh-axi, ast-grep). Код на выходе не меняется, меняется только стоимость (затраты токенов).
  Оценивается на небольших задачах «только для чтения» с заранее известными правильными ответами. Процесс **полностью
  автоматизирован**.
- **Категория F (real tasks / реальные задачи).** Инструменты, которые меняют *результат* работы (например: OpenSpec,
  ponytail, sdd-kit целиком). Для проверки нужна реальная задача (тикет), контрольные точки, git diff и слепое
  оценивание. Процесс **полуавтоматический**: оценка результатов делается людьми вручную.

## Быстрый старт

```bash
uv sync
uv run bench arms list
uv run bench arms validate
```

## Структура репозитория

```text
arms/                  YAML-спецификации веток тестирования (одна ветка = один инструмент, без группировок)
probes/templates/      шаблоны проверок для категории P (настраиваются под каждый репозиторий)
src/cc_bench/          сам CLI-инструмент
results/               результаты каждого запуска (добавлено в .gitignore)
docs/                  проектная документация, архитектурные решения (ADR) и регламент
```

## Проектная документация

Вся логика решений, ADR и регламент тестирования теперь хранятся в этом репозитории в папке `docs/` (
`docs/PLAN-tools.md`, `docs/adr/`). Изначально они находились в проекте `sdd-kit` (`/home/octrow/cybernet/sdd-kit`), а
затем были перенесены сюда.

## Важные правила тестирования

- **Один инструмент на одну ветку тестирования.** Никаких связок и групп инструментов (бандлов).
- **Обязательная проверка срабатывания.** Если во время тестового (smoke) запуска нет доказательств, что инструмент
  реально активировался, его нужно починить или убрать. Неработающие инструменты к основным тестам не допускаются.
- **Главная метрика времени — «активное время»** (время работы процессора/агента), а не обычное время по часам (wall
  clock).
- **В итоговом отчете** обязательно должна быть статистика использования инструмента и раздел с конкретными
  рекомендациями по его улучшению.
