# cc-bench

Реально ли помогает тот или иной инструмент Claude Code? cc-bench это измеряет.

Вы даёте ему целевой репозиторий и **один** инструмент (навык, CLI-утилиту,
MCP-сервер или артефакты вроде OpenSpec). Он прогоняет одни и те же
замороженные задачи с инструментом и без него — в headless-сессии Claude Code
с включённой телеметрией — и выдаёт цифру, которую можно положить в ADR:
стоимость, токены, активное время, число вызовов инструментов, верный ответ
или нет.

Главное правило: одна ветка (arm) = один инструмент, никаких связок. Если
непонятно, какой именно инструмент сдвинул цифру, цифра бесполезна.

## Две категории

**Категория P — probes (проверки).** Для инструментов, которые меняют то,
*как* агент собирает контекст (rtk, graphify, gh-axi, ast-grep,
chrome-devtools-axi). Код на выходе не меняется — меняется стоимость.
Небольшие задачи «только для чтения» с заранее замороженным правильным
ответом, полностью автоматизировано. Уже пройдено, см. [статус](#статус).

**Категория F — real tasks (реальные задачи).** Для инструментов, которые
меняют *результат* работы (OpenSpec, ponytail, sdd-kit). Нужны реальный тикет,
контрольные проверки, git diff и слепая оценка человеком. Полуавтоматично —
оценивание ручное. Ещё не запускалось.

## Быстрый старт

```bash
uv sync
uv run bench arms list        # что вообще можно измерить
uv run bench arms validate    # проверить arms/*.yaml
```

## Как проходит одно измерение

1. **Заморозить задачу.** Проба (категория P) или тикет (категория F) плюс
   эталонный ответ — записаны и больше не меняются. Изменённый эталон = новая
   проба, а не правка старой.
2. **Подготовить ветки.** `bench prepare --repo <путь> --arm <имя>` клонирует
   целевой репозиторий в `~/bench/`, ставит метку коммита `bench-base` и
   устанавливает инструмент в изолированный `CLAUDE_CONFIG_DIR`, чтобы ветки
   не влияли друг на друга.
3. **Smoke-прогон — проверка срабатывания.** По одному дешёвому промпту на
   ветку (`smoke/*.md`), который обязан доказать, что инструмент действительно
   активировался. Нет доказательства — нет измерения: такую ветку чинят или
   выбрасывают.
4. **Измерить.** `bench run --arm ... --tier p --task ... --runs 3` — headless
   прогоны с телеметрией OTEL. Базовая ветка и ветка с инструментом чередуются
   прогон за прогоном, чтобы дрейф бил по обеим одинаково.
5. **Оценить и собрать отчёт.** `bench gates` (diff + ruff/pytest/охват
   изменений, только категория F), `bench extract` превращает OTEL и стенограмму
   в одну строку CSV, `bench report` строит сравнение по медиане и IQR.

Для измеряемых прогонов нужен локальный OTEL-коллектор на `localhost:4317`.
Время считается по **активному времени**, а не по часам — wall clock в
основном измеряет очередь к API.

## Команды

| Команда | Что делает |
|---|---|
| `bench arms list` / `validate` | список / проверка схемы описаний веток |
| `bench prepare` | клонировать целевой репозиторий и установить одну ветку |
| `bench run` | headless-прогон(ы) для одной ветки |
| `bench gates` | diff + ruff/pytest/охват изменений относительно `bench-base` |
| `bench extract` | OTEL + стенограмма → одна строка `results.csv` |
| `bench report` | markdown-отчёт с медианой и IQR |

У `probes gen|freeze` и `smoke` нет подкоманд — эти шаги ведёт кондуктор
(отдельная сессия Claude) через `probes/templates/` и `smoke/run-*.sh`.

## Структура репозитория

```
arms/                  описания веток, по одному YAML на инструмент (гипотеза, метрика, установка, fired-check)
probes/templates/      generic-шаблоны проб категории P с плейсхолдерами
probes/<repo>/         замороженные пробы под конкретный репозиторий — после заморозки не правятся
smoke/                 по одному промпту-проверке срабатывания на ветку + скрипты запуска
src/cc_bench/          сам CLI
docs/                  план, ADR, глоссарий
results/               результаты прогонов, отчёты, логи (в .gitignore — только локально)
```

## Пример ветки целиком

```yaml
name: rtk
tier: p
hypothesis: rtk's token-optimized bash output proxy cuts input tokens per probe versus raw bash output.
primary_metric: input_tokens_per_probe
install:
  - kind: path_binary
    check: command -v rtk
  - kind: hook
    text: Install the rtk PreToolUse Bash rewrite hook into the arm's CLAUDE_CONFIG_DIR settings.json.
  - kind: claude_md_hint
    text: RTK is available - a token-optimized CLI proxy that cuts up to 90% of bash output.
fired_check:
  kind: command_delta
  command: rtk gain
```

У каждой ветки должна быть опровержимая гипотеза, одна главная метрика и
fired-check. Нет fired-check — нет ветки.

## Статус

**Категория P: завершена (2026-07-30).** 5 замороженных проб × (базовая ветка +
один инструмент), 6 раундов, 66 прогонов. Раунды 1–3 — инструмент установлен,
но не «прорекламирован»; раунды 4–6 — добавлена подсказка в CLAUDE.md. Главный
вывод: подсказка заставила сработать 3 инструмента из 6 (graphify, gh-axi,
chrome-devtools-axi) и ничего не изменила для остальных трёх (ast-grep, rtk,
headroom) — текст в файле памяти не уводит модель от встроенного инструмента,
который и так решает задачу. Полный разбор — в `results/tier-p-report.md`
(локально, в .gitignore).

**Ветка headroom выпилена 2026-07-31**: сжатие 0–2%, ломает префикс
prompt-кэша, +45..62% к счёту. Обоснование — в sdd-kit
`docs/ADR/ADR-0014-drop-headroom.md`. Поэтому в `arms/` 10 веток, а в отчёте
категории P — 11.

**Категория F: не начата.** Определены 5 веток (openspec, ponytail, caveman,
grill-with-docs, sdd-kit); нужны реальный тикет, гейты и слепая оценка.
Два блокера тянутся со smoke-прогонов: **caveman и ponytail не срабатывают** —
навык установлен, но ни разу не активируется, — значит по регламенту их чинят
или выкидывают, а не измеряют. Ветка `sdd-kit` описывает движущуюся цель: её
клон заморожен на версии кита от 2026-07-30, а сам кит с тех пор ушёл вперёд —
перед заморозкой прочитайте шапку `results/sdd-kit-static-check.md`.

CLI: `arms`, `prepare`, `gates`, `run`, `extract`, `report` работают и
использовались в фазе категории P. Extractor проверен на реальных сессиях
m1/m2 — стоимость и активное время совпадают с ранее опубликованными цифрами.
