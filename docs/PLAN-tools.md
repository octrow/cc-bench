# План: инструмент бенчмарка Claude Code ДО/ПОСЛЕ (skill / tool / sdd / etc)

Дата: 2026-07-30. Решения зафиксированы в `adr/ADR-0001..0005`, термины - в `adr/glossary.md`.

## 1. Контекст - зачем и почему именно так

Мы дважды (m1, m2) сравнили "WBN с sdd-kit vs без" и оба раза харнесс
собирался руками: клоны и армы - `/home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/prepare-m2.sh`, гейты и диффы -
`/home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/finish-tails.sh`, телеметрия - export-блок из /home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/MANUAL.md, активное
время - ручной пересчёт транскриптов. Выводы получились, но каждый
новый замер - снова ручная сборка, а методологические ошибки m1
(утечка контекста, судья с чужим baseline, гейты после прогонов)
случились именно из-за ручной сборки на ходу.

Цель теперь другая: не "ещё один эксперимент", а **инструмент** -
отдельный репозиторий, который для любой пары (репо, тулза) выдаёт
повторяемую цифру ДО/ПОСЛЕ: openspec, skills (ponytail, caveman,
grill-with-docs), rtk, graphify, headroom, gh-axi, ast-grep,
chrome-devtools-axi, целый sdd-kit.

Ключевая идея дизайна: тулзы делятся на два класса, и мерить их надо
по-разному (ADR-0002):

- **Tier P (пробы).** Тулзы, меняющие КАК агент добывает контекст
  (rtk, headroom, graphify, gh-axi, ast-grep, chrome-devtools-axi).
  Код на выходе не меняется - меняется цена. Меряем на маленьких
  read-only задачах с заранее известным ответом. Дёшево (центы за
  прогон), полностью автоматом, n=3 без боли.
- **Tier F (реальные задачи).** Тулзы, меняющие ЧТО производится
  (openspec, skills, sdd-kit целиком). Нужен реальный тикет, гейты,
  дифф, слепое судейство. Дорого - поэтому пилот 1 прогон, и только
  армы с дельтой выше шума идут на 3 прогона.

Полная матрица (11 арм × 3 задачи × 3 прогона, всё судимое) - это
~100 сессий; m1+m2 стоили ~$80 за 4 сессии. Двухтировая схема - способ
получить сигнал за разумные деньги.

### CLI (эскиз)

```
bench prepare --repo <path> --arm rtk        # клон, bench-base, cfg, установка тулзы, fired-check smoke
bench probes gen --repo <path>               # LLM инстанцирует шаблоны проб; человек правит и замораживает
bench run --arm rtk --tier p --runs 3        # headless-прогоны с OTEL-тегами, интерливинг с baseline
bench run --arm openspec --tier f --task WEB-XXXX   # полуавто: прогон+гейты+дифф+анонимизация
bench report                                 # csv -> markdown: median+IQR, дельта, tool-usage, советы
```

## 3. Армы v1 - гипотеза, метрика, fired-check

Правило: одна тулза на арму, никаких бандлов. Арма, у которой
fired-check не сработал в smoke-прогоне, чинится или выкидывается -
измеряемые прогоны на мёртвую арму не тратим (урок Ponytail в тесте
JetBrains: skill установлен, но ни разу не активировался).

| Арма | Tier | Что должна менять | Первичная метрика | Fired-check |
|---|---|---|---|---|
| T0 baseline | - | эталон | - | - |
| openspec (спеки посеяны) | F | точность наведения на контекст | $ на принятую задачу | чтение `openspec/specs/*` в tool_result |
| ponytail | F | меньше overbuild, короче дифф | размер диффа при равном task_success | `skill_activated{skill.name=ponytail}` |
| caveman | F | короче проза | output-токены | `skill_activated` |
| grill-with-docs | F | решения через вопросы, ADR | task_success + вмешательства | `skill_activated` |
| sdd-kit целиком | F | весь процесс | $ на принятую задачу | `make sdd-check` + skill_activated |
| rtk | P | меньше bash-выхлопа | input-токены на пробу | дельта `rtk gain` |
| graphify (кэш посеян) | P | быстрее навигация | прочитано:изменено файлов, input-токены | чтение `graphify-out/*` |
| headroom | P | компрессия контекста | input+cacheRead токены | дельта `headroom_stats` |
| gh-axi | P | дешевле GitHub-запросы | токены на gh-пробу | вызовы gh-axi в Bash |
| ast-grep | P | дешевле структурный поиск | токены на поиск-пробу | вызовы `ast-grep`/`sg` |
| chrome-devtools-axi | P | дешевле инспекция веба | токены на web-пробу | вызовы тулзы |

Для CLI-тулз (rtk, gh-axi, ast-grep, chrome-devtools-axi) арма = бинарь
на PATH + одна hint-строка в CLAUDE.md о его существовании: доступность
без подсказки - заведомый ноль, hint - часть тулзы.

## 4. Метрики

Автоматом на каждый прогон (строка в results.csv):

- Токены по типам (input/output/cacheCreation/cacheRead) **и по моделям**;
  cost_usd; cache hit rate - из OTEL (`claude_code.token.usage`,
  `claude_code.cost.usage`), теги `arm/task/run` через
  `OTEL_RESOURCE_ATTRIBUTES`.
- Turns, tool calls и их разбивка, прочитано:изменено файлов,
  компактификации, api errors - OTEL events + транскрипты.
- **Активное время** - из транскриптов, паузы ожидания юзера вырезаются
  (алгоритм /home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/comparison-runs.md). Wall clock - справочная колонка.
- Fired-check армы (bool + чем подтверждён).
- Tier P: правильность ответа по answer key (0/1).
- Tier F: гейты (дифф применяется, ruff - только новые нарушения,
  pytest - только новые падения, scope creep vs замороженный blast
  radius), размер диффа.

Судейские (Tier F, ручной шаг): task_success 0/0.5/1, рубрика 1-5,
"влил бы я это" - вслепую, per-arm baseline.

## 5. Протокол честности (заморозить до прогона 1, потом не трогать)

Уроки m1/m2, вшитые как правила инструмента:

1. Один prompt-пакет (тикет + AC) на обе армы, идентичный, заморожен
   до любых прогонов. Никаких уточнений на ходу.
2. Гейты и blast radius калибруются на baseline ДО прогона 1.
3. Порядок арм интерливится (T0,Tx,Tx,T0,...), прогоны строго
   последовательно, во время сессии на машине ничего тяжёлого.
4. Пробы и answer keys заморожены до прогонов; ключи проверил человек.
5. Правило падений: упавший прогон перезапускается один раз; второе
   падение = success 0.
6. Модель/effort/permission mode/версия claude/SHA - одинаковые везде,
   записаны в снапшот.
7. Стоимость установки тулзы (генерация спек, graphify-кэша, kit)
   логируется отдельно -> break-even в отчёте.
8. Бюджет-кап на эксперимент фиксируется заранее (дефолт $60: ~$15
   Tier P, ~$45 Tier F); инструмент считает spend из OTEL после каждой
   пачки и останавливается на капе.
9. Если внутриармный разброс больше межармной дельты - вердикт
   "нет сигнала", а не победитель.

## 6. Фазы работ (кондуктор = этот чат, Fable 5)

Роли: Fable - кондуктор (протокол, теги, агрегация, отчёт);
sonnet-субагенты - механика (скаффолд, портирование скриптов,
экстрактор); opus/fable-субагент - слепой судья.

- **Фаза 0 - скаффолд репо** (sonnet): pyproject (uv), CLI-скелет,
  каталог `arms/*.yaml` (11 арм из §3), шаблоны проб, README.
- **Фаза 1 - портирование харнесса** (sonnet): /home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/prepare-m2.sh ->
  `bench prepare` (клон, bench-base, .env, cfg-per-arm,
  `--strict-mcp-config` для baseline); /home/octrow/cybernet/sdd-kit/docs/archive/benchmark-m1-m2/finish-tails.sh -> гейты;
  OTEL-блок; экстрактор метрик (OTEL + транскрипты + активное время).
- **Фаза 2 - smoke**: каждая арма проходит fired-check на дешёвом
  промпте; go/no-go таблица. Мёртвые армы чиним или выкидываем здесь.
- **Фаза 3 - Tier P на WBN**: пробы сгенерены и заморожены; ~5 проб ×
  2 армы × 3 прогона на каждую P-тулзу; отчёт median+IQR. Тулзы без
  сигнала - готовый вывод "нет эффекта при n=3".
- **Фаза 4 - Tier F пилот**: 2 задачи (багфикс + маленькая фича),
  1 прогон/арму -> промоушен выживших на 3 прогона.
- **Фаза 5 - судейство**: LLM вслепую, правильные baseline; Daniil
  перепроверяет треть.
- **Фаза 6 - итоговый отчёт**: вердикт по каждой тулзе
  (keep / drop / keep-with-caveat), break-even, честные "нет сигнала",
  и обязательный раздел **"советы по улучшению sdd-kit"**: что не
  активировалось, что жгло токены впустую, что добавить/убрать
  (по ADR-0005 отчёт без этого раздела неполон).

## 7. Что сознательно НЕ делаем в v1

- Чужие/публичные репо (v2: пробы обкатаны - добавить curated-полигоны).
- Grafana/DuckDB-дашборды (CSV+markdown хватает до десятков прогонов).
- Автоматизацию судейства "до конца" (судья - отдельный ручной шаг).
- Enhanced-tracing beta, арму "daily-config" - round 2, если Фаза 6
  оставит вопросы.

## 8. Риски

- Auth свежих `CLAUDE_CONFIG_DIR`: только подписка/OAuth (setup-token),
  никаких API-ключей; логин в каждый cfg - разовый ручной шаг prepare.
- `--strict-mcp-config` не перекрывает `disabledMcpServers` из
  `~/.claude.json` - проверять по `mcp_server_connection`.
- JSONL занижает output-токены (~2×) - токены и деньги берём из OTEL,
  транскрипты только для структуры (turns, tool calls, активное время).
- LLM-судья дрейфует - ловится человеческой третью (ADR-0004).
